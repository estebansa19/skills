### Change

**You own the design and the proof.**

1. In an unfamiliar area, run the `how` skill over the code you will touch. Otherwise read it and
   its neighbours.
2. Name the data shape before writing logic (Foundational Thinking, Model the Domain).
3. Design It Twice when there is more than one reasonable shape. Measure the Number when the
   request rests on a quantity.
4. Make the change with the `build` skill.
5. Prove It Works on the real surface: run the feature, read the stored value, measure the after.
6. Look for the Same Problem Elsewhere, and report what is outside the change.
7. Commit locally with the `commit` skill, in small ordered commits (Sequence Verifiable Units).
   Run the ship playbook only when the user asked to ship.

**Reply:** what changed for the user, the design chosen and the ones rejected, how you proved it,
what you found elsewhere, and the open decisions.
